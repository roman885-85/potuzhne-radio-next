# Спектр с VS1053b во время декодирования MP3/AAC

Дата: 2026-09-22. Всё ниже проверено по официальным файлам VLSI (скачаны и распакованы),
по даташиту VS1053b и по рабочему проекту на ESP32. Там, где вывод получен рассуждением,
а не взят из документа, это отмечено явно.

**Короткий ответ: да, это возможно и делается штатным плагином VLSI. Но за это придётся
отдать FLAC** — плагин спектра несовместим с той версией патча, которая стоит в проекте сейчас.

---

## 1. Плагин существует

Официальный плагин: **Spectrum Analyzer Plugin v1.10**, файл `spectrumAnalyzer-110.zip`.

- Страница: <http://www.vlsi.fi/en/support/software/vs10xxplugins.html>
  (раздел «VS1053b Plugins», не `vs10xxapplications.html` — там спектра для VS1053b нет,
  только для VS1003b ADC)
- Архив: <https://www.vlsi.fi/fileadmin/software/VS10XX/spectrumAnalyzer-110.zip>
- Документация: <https://www.vlsi.fi/fileadmin/software/VS10XX/spectrumAnalyzer.pdf>

В архиве для VS1053b три варианта:

| Файл | IRAM | X-RAM | AIADDR | Размер `plugin[]` |
|---|---|---|---|---|
| `spectrumAnalyzer1053b.plg` | 0x050..0x20e | 0x1800..0x187f | 0x0050 | 950 слов |
| `spectrumAnalyzerAppl1053b.plg` | 0x050..0x228 | 0x1800..0x187f | 0x0050 | 1002 слова |
| **`spectrumAnalyzerAppl1053b-2.plg`** | **0xd00..0xed8** | **0x1810..0x1877** | **0x0d00** | **1000 слов** |

Работает ли во время декодирования MP3/AAC — **да**. Документ прямо говорит: «The analyzer
works for all audio file types», плагин стартует сам после загрузки. Линейный вход не нужен.
Подтверждение от сотрудника VLSI (Pasi) на форуме: «SCI is completely hardware, so it works
the same whatever the core is doing» —
<https://www.vsdsp-forum.com/phpbb/viewtopic.php?t=482>

**Реальный работающий пример на ESP32** (не теория):
<https://github.com/blotfi/ESP32-Radio-with-Spectrum-analyzer> — веб-радио ESP32 + VS1053b +
ILI9341, 14 полос. Я сверил их массив `analizer[1000]` в `src/patches.h` побайтово с
официальным `spectrumAnalyzerAppl1053b-2.plg` — **совпадает точно**. Чтение спектра у них в
`src/Esp32_radio.cpp`, функция `VS1053::getBands()`, опрос раз в 100 мс.

Важная деталь про этот проект: у них строка `LoadUserCode(plugin, PLUGIN_SIZE)` (патч)
**закомментирована**, грузится только анализатор. То есть они не совмещали патч и спектр —
они отказались от патча целиком. См. п. 3.

## 2. Полосы, адреса, чтение

Для `spectrumAnalyzerAppl1053b-2` (единственный вариант, годный к совмещению с патчем):

- **BASE = 0x1810** (у обычных версий 0x1800)
- **Полос: 14 по умолчанию, максимум 15** (у обычных версий максимум 23)
- Частоты по умолчанию: **50, 79, 126, 200, 317, 504, 800, 1270, 2016, 3200, 5080, 8063,
  12800, 20319 Гц**. Это номиналы; фактические центры отличаются и **плавают вместе с
  частотой дискретизации**. Пример из документа для 44.1 кГц: 43, 64, 107, 193, 301, 473,
  775, 1205, 1894, 2756, 4823, 7579, 12403, 19982 Гц.
- При частоте дискретизации ниже 44100 Гц **верхние полосы будут пустыми** — это нормально.

Карта памяти X-RAM (читается через `SCI_WRAMADDR` = регистр 7, затем `SCI_WRAM` = регистр 6,
адрес автоинкрементится):

| Адрес | Поле |
|---|---|
| 0x1811 | `rate` — частота дискретизации (запись 0 сюда = «пересчитай полосы») |
| 0x1812 | `bands` — сколько полос реально используется |
| 0x1814 .. 0x1823 | `results` — значения полос (16 слов под максимум 15 полос) |
| **0x1868 .. 0x1876** | `frequencies` — таблица частот для настройки полос |

Обратите внимание: таблица частот у `-2` осталась по **абсолютному** адресу 0x1868, а не
BASE+0x68. Это прямо написано в документе и подтверждается загрузочной таблицей `.cmd`
(там `W 2 7 1868` и следом 14 частот + терминатор 0x61a8 = 25000).

Формат слова результата (одинаков у всех версий):

```
биты  5..0  — текущее значение, 0..31, шаг 3 dB
биты 11..6  — пиковое значение, 0..31, шаг 3 dB
```

Пик даётся чипом бесплатно в том же слове — для «шапочек» над столбиками на Nextion
отдельный код не нужен. В примере blotfi пик выбрасывается (`val & 31` после приведения
к `uint8_t`) и рисуется свой — так делать необязательно.

Код чтения (адаптация официального примера под BASE 0x1810):

```cpp
#define SA_BASE 0x1810
uint8_t bands;
uint8_t cur[15], peak[15];

write_register(SCI_WRAMADDR, SA_BASE + 2);
bands = read_register(SCI_WRAM);            // обычно 14
write_register(SCI_WRAMADDR, SA_BASE + 4);
for (uint8_t i = 0; i < bands; i++) {
    uint16_t v = read_register(SCI_WRAM);   // адрес сам инкрементится
    cur[i]  =  v        & 0x3F;
    peak[i] = (v >> 6)  & 0x3F;
}
```

Неиспользуемые полосы чип держит в нуле, так что `bands` можно вообще не читать и всегда
брать фиксированные 14 слов.

### Как часто опрашивать и сколько это стоит по SPI

Документ рекомендует **5..20 раз в секунду**. blotfi опрашивает раз в 100 мс (10 Гц).

Одна SCI-транзакция = 32 бита (опкод + адрес + 16 бит данных). Полное чтение 14 полос —
17 транзакций (2 записи `WRAMADDR` + 15 чтений).

В этом проекте `VS1053_SPI_CTL` выставлен в **250 кГц**
(`audioVS1053Ex.cpp:304`) — это очень осторожно:

| Тактовая SPI | Одна транзакция | Кадр из 14 полос | При 20 Гц |
|---|---|---|---|
| 250 кГц (сейчас) | ~128 мкс | ~2.2 мс (+накладные, реально 2.5–3 мс) | ~4–6 % времени шина занята |
| 4 МГц | ~8 мкс | ~0.14 мс | ~0.3 % |

Потолок для **чтения** по SCI — `CLKI/7` (даташит VS1053b, раздел электрических
характеристик). В проекте `SCI_CLOCKF = 6 << 12` → SC_MULT=3 → **CLKI = 3.0 × 12.288 =
36.864 МГц**, значит потолок чтения ≈ **5.27 МГц**, и комментарий в коде («allows SPI
clocking at 5 MHz, 4 MHz is safe») это подтверждает. Записи допускают `CLKI/4`.

То есть 250 кГц можно безопасно поднять до 4 МГц — это заодно сократит и загрузку самих
плагинов на старте (см. п. 4).

### Чтение фактических центров полос (необязательно)

Официальный код для обычной версии: слово по `BASE + 0x1c + 3*i`, затем
`freq = (long)rate * a >> 11`.

Для `-2` этот адрес в документе **не указан**. По структуре он выводится: поле `results`
занимает 16 слов от BASE+4, значит следующее поле начинается с BASE+0x14 = **0x1824 + 3*i**
(у обычной версии BASE+4+24 = BASE+0x1c, сходится). **Это мой вывод, а не документ** — на
железе не проверял. Для подписей под столбиками проще взять номинальную таблицу из п. 2.

## 3. Конфликт с `vs1053b-patches-flac` — да, прямой

Сейчас в проекте (`vs1053b-patches-flac.h`, шапка ссылается на `vs1053b-patches290.zip`)
загружается **патч с FLAC-декодером**. Я скачал пакет и сверил:

| Вариант патча | IRAM | Размер `plugin[]` |
|---|---|---|
| `vs1053b-patches.plg` (базовый) | 0x50..0x2f8, 0x300..0x888 | 4667 слов |
| `vs1053b-patches-latm.plg` | 0x50..0xa48 | 5596 |
| `vs1053b-patches-pitch.plg` | 0x50..0xafa | 5966 |
| **`vs1053b-patches-flac.plg` (стоит сейчас)** | **0x50..0xf8e** | **8414** |
| `vs1053b-patches-flac-latm.plg` | 0x50..0xffb | 8590 |
| `vs1053b-patches-dsd.plg` | 0x50..0xf8d | 8736 |

Анализатор `-2` живёт в IRAM **0xd00..0xed8**. Это **внутри** 0x50..0xf8e — FLAC-патч и
анализатор физически перетирают друг друга. Отсюда и фраза в документации VLSI:

> «Note that the vs1053b patches package cannot be used with the default spectrum analyzer
> version, but the package **without FLAC decoder** can be used with `spectrumAnalyzerAppl1053b-2`.»

Плюс два независимых конфликта у *обычных* версий анализатора (`spectrumAnalyzer1053b.plg`,
`spectrumAnalyzerAppl1053b.plg`), из-за которых они не годятся вообще ни с каким патчем:
- они грузятся в IRAM 0x050.. — прямо поверх кода патча;
- они пишут в `SCI_AIADDR` значение **0x0050** — тот же самый хук, которым стартует патч;
- их X-RAM начинается с 0x1800, а патч держит там 32-битный счётчик сэмплов.

`-2` решает все три: IRAM 0xd00, AIADDR 0x0d00, X-RAM с 0x1810.

### Можно ли грузить оба

**Да — базовый `vs1053b-patches.plg` + `spectrumAnalyzerAppl1053b-2.plg`.**

Порядок: **сначала патч, потом анализатор.** Механика такая: патч в самом конце своей
таблицы пишет 0x50 в `SCI_AIADDR`, чтобы стартовать, и, по документу патча, «do not use it
afterwards» — то есть после запуска хук `AIADDR` свободен. Анализатор затем забирает его
себе, записав 0x0d00. Если сделать наоборот, патч перезапишет `AIADDR` и анализатор
замолчит. (Порядок — мой вывод из этих двух фактов; в явном виде VLSI его не документирует.
Аналогичная рекомендация «патч первым, плагин вторым» встречается в обсуждении ADMon EQ.)

### Что теряем

**Только FLAC.** Всё остальное из пакета патчей остаётся, в том числе:

- **VU meter** (`SCI_STATUS` бит 9 → `SCI_AICTRL3`) — то, чем проект пользуется сейчас;
- исправления MP3 bit reservoir, AAC/MP4, Vorbis, MP2;
- счётчик сэмплов, `SS_DO_NOT_JUMP`, sample-rate finetuning и т. д.

FLAC-декодер — это отдельный раздел 1.7 документа патча и он есть только в `-flac`
вариантах. VU meter — общая функция пакета, описана в разделе «New and Extended Features»
и присутствует в базовом `vs1053b-patches.plg`.

Побочный плюс: базовый патч почти вдвое меньше FLAC-версии (4667 слов против 8414), так что
даже вместе с анализатором (1000 слов) во флеше ESP32 получится **экономия ~5 КБ**, а не
расход.

**Предупреждение.** Есть форумный случай, когда заявленная совместимость не сработала:
пользователь грузил ADMon EQ + анализатор и получил неработающую связку
(<http://www.vsdsp-forum.com/phpbb/viewtopic.php?t=354>). Это другая пара плагинов, но
говорит о том, что связку `patches + Appl-2` нужно проверять на железе, а не считать
гарантированной.

## 4. Подводные камни

**Объём.** Анализатор `-2` — 1000 слов `plugin[]` = 2 КБ флеша ESP32, 970 записей по SCI при
загрузке. На текущих 250 кГц это ~124 мс загрузки. Базовый патч — 4676 записей, ~600 мс.
Итого ~0.72 с на старте. Сейчас один только FLAC-патч (8423 записи) занимает ~1.08 с. Если
поднять `VS1053_SPI_CTL` до 4 МГц, обе загрузки схлопнутся до ~45 мс.

**Перезагрузка после сброса.** Оба документа говорят одно и то же:

- **Аппаратный сброс** — перегружать и патч, и анализатор полностью.
- **Программный сброс** (`SM_RESET`) — патч перегружать полностью; анализатору, по
  документу, достаточно «либо заново записать частоты, либо перегрузить плагин»
  (перезапись `AIADDR` = 0x0d00 при этом, очевидно, тоже нужна).
- **После sine test / memory test** — они выполняются через `SM_TESTS` и завершаются
  программным сбросом, значит действует правило выше. В текущем драйвере sine test не
  используется вообще (в `audioVS1053Ex.cpp` его нет).

**Смена потока/станции перезагрузки не требует.** В этом драйвере `softReset()` вызывается
ровно один раз — в `begin()` (`audioVS1053Ex.cpp:313`), смена станции идёт через
`stopSong()`/`SM_CANCEL`. Так что плагины переживают переключение станций. Но если этот
порядок когда-нибудь поменяется и `softReset()` начнут звать на каждую станцию — спектр и
VU умрут молча.

**Порядок инициализации в текущем коде уже подозрительный.** `setVUmeter()` вызывается на
строке 322, а `loadUserCode()` — на 325, то есть бит VU взводится **до** загрузки патча.
Сейчас это как-то работает, но при добавлении второго плагина лучше привести к очевидному
порядку: патч → анализатор → `setVUmeter()`.

**Нагрузка на DSP и качество декодирования.** По документу VLSI: анализатор при 14 полосах и
44.1 кГц ест **~1.6 МГц** на VS1053 (это «более точная» версия), VU meter — ещё **~0.6 МГц**.
В проекте `SC_MULT=3.0` (CLKI = 36.864 МГц) и **`SC_ADD = 0` — автоматический подъём частоты
запрещён**. Для MP3 запас есть, а вот HE-AAC/AAC+ — это тот случай, ради которого SC_ADD и
существует (даташит: автоподъём работает только на WMA и AAC). Риск: заикания на тяжёлых
AAC-потоках. Лечится одним словом: `SCI_CLOCKF = 0x6800` (те же 3.0× плюс разрешение
добавить до 1.0×, т. е. до 4.0× = 49 МГц). Это заодно поднимет потолок SCI-чтения до ~7 МГц.
Минус — больше нагрев и потребление.

**Ограничений по битрейту нет.** Формат тоже любой («works for all audio file types»).
Единственное ограничение — по частоте дискретизации: ниже 44100 Гц верхние полосы пустые.

**Полос максимум 15, а не 23.** Если захочется 20+ столбиков на Nextion — с патчем это
невозможно, только без патча (и тогда без FLAC *и* без VU).

**Настройка своих частот** (если 14 стандартных не устроят): записать новые частоты по
возрастанию начиная с 0x1868, закрыть список значением 25000, затем записать 0 в поле
`rate` (0x1811) — это заставит чип пересчитать фильтры.

## 5. Если плагин не пойдёт — что ещё есть

Честно: ничего, что дало бы настоящий спектр «из коробки».

**VU meter (то, что уже есть).** `SCI_STATUS` бит 9 включает, `SCI_AICTRL3` отдаёт два
байта: старший — левый канал, младший — правый. Шкала **0..96, шаг 1 dB** (0 = тишина,
96 = клиппинг; на практике максимум 95). Важно: это новая шкала начиная с ревизии 2.3
патча — в старых было 0..31 по 3 dB. Громкость (`SCI_VOL`) в расчёт не берётся. Это два
числа уровня, спектра из них не сделать. Кстати, текущий `computeVUlevel()` делает
`map(..., 85, 92, 0, 255)` — то есть использует лишь узкое окно 85..92 из доступных 0..96.

**`SCI_HDAT0` / `SCI_HDAT1` — не спектр.** По даташиту VS1053b (раздел 9.6.9) там только
заголовок потока:
- MP3: `HDAT1` = 0xFFE0..0xFFFF (syncword, ID, layer, protect), `HDAT0` = индекс битрейта,
  индекс частоты дискретизации, pad, mode, emphasis;
- AAC ADTS = 0x4154 «AT», ADIF = 0x4144 «AD», .m4a = 0x4D34 «M4»; WMA = 0x574D; Ogg = 0x4F67;
  WAV = 0x7665 — и в `HDAT0` средний поток данных в байтах/с.

Полезно для «что играет», для спектра бесполезно.

**Счётчик сэмплов X:0x1800** (32 бита, из пакета патчей) — позиция воспроизведения, не спектр.

**Свой FFT на ESP32 через I2S-выход VS1053b.** Это единственный настоящий запасной вариант.
У VS1053b есть 16-битный **I2S-выход** для внешнего ЦАП (даташит, раздел 11.14), на
GPIO4–GPIO7 (`I2S_LROUT`, `I2S_MCLK`, `I2S_SCLK`, `I2S_SDATA`). Включается записью в WRAM:
`SCI_WRAMADDR = 0xC017` (GPIO DDR) и `SCI_WRAMADDR = 0xC040`, значение `0x000C` в
`I2S_CONFIG`. ESP32 принимает это как I2S-вход и считает свой FFT — сколько угодно полос,
полный контроль, аналоговый выход при этом продолжает играть.

Оговорка: нужны разведённые GPIO4–7. На дешёвых модулях VS1053 они обычно **не выведены** на
гребёнку (выведены GPIO0–3 и управляющие). Перед тем как всерьёз рассматривать этот путь,
надо посмотреть на конкретную плату TehCeh.

**Аналоговый выход в АЦП ESP32** — теоретически возможно, но ADC у ESP32 шумный и занят;
как решение для радио не рекомендую.

## Что я бы сделал в этом проекте

1. Заменить `vs1053b-patches-flac.h` на базовый `vs1053b-patches.plg` (4667 слов).
   FLAC в интернет-радио и так почти не встречается, а VU и все исправления остаются.
2. Добавить вторым массивом `spectrumAnalyzerAppl1053b-2.plg` (1000 слов).
3. Порядок в `begin()`: `softReset()` → CLOCKF → патч → анализатор → `setVUmeter()`.
4. Поднять `VS1053_SPI_CTL` с 250 кГц до 4 МГц (потолок 5.27 МГц при текущем CLKI).
5. `SCI_CLOCKF` — рассмотреть 0x6800 вместо 0x6000, если после включения спектра начнутся
   заикания на AAC.
6. Опрос — 10–20 Гц, читать оба поля (текущее и пик) одним словом.

Проверять обязательно на железе: документально связка разрешена, но живого примера
именно «патч + Appl-2 одновременно» я не нашёл — blotfi грузит только анализатор, без патча.
